# Daniel App Agent Guide

This repository is evolving from a small-group devotional app for "Daniel and his Friends" into a branch-church app that can support multiple local churches, regional administration, resources, announcements, and devotional content.

## Version Purpose

- Current branch: `codex/figma-design-merge`.
- Current implementation target: merge the new Figma direction into the existing iOS app and prepare the product structure for a larger church-management app.
- Primary user-facing navigation: Daily Verse, Connect, Resources, Settings.
- Backend database cleanup, regional role hierarchy, and admin portal upgrades are planned but should not be rushed into the Figma UI merge unless a branch explicitly targets those systems.

## Product Direction

- The original app identity served a Chinese mission group inside the global church.
- The new product should scale to branch churches while preserving the devotional warmth of the original app.
- "Group" from Figma should be interpreted as Connect: church communication, not a generic social group.
- The Settings experience should be a full page, not a floating window.
- Resources should behave like a simple church resource library/directory for hymnbook, church documents, useful links, Bible study, Bible seminar, and other shared materials.
- Word Cards and Praise remain reusable legacy Firebase-backed content areas, but they are not first-level Resources entries in this phase.
- Authentication should move toward regional hierarchy later: global/admin, region admin, branch/local admin, and member access.

## Language Requirements

- The app must support Chinese, English, and Korean for new user-facing strings.
- Do not add a visible string in only one language unless it is temporary debug text or a backend-only identifier.
- Prefer `CoreModels.VerseLanguage` for language switching.
- Use existing localization patterns in `LocalizedText.swift` when the string is shared across screens.
- For screen-local copy, localized helper methods inside the SwiftUI view are acceptable, but promote repeated strings into `LocalizedText.swift`.
- Chinese should be the primary review language for product decisions because the original ministry audience is Chinese-speaking.

## Design Direction

- Follow the new Figma design/screenshots as the visual source of truth for Daily Verse, Connect, Resources, and Settings.
- Preserve existing app data models and services unless a branch specifically targets backend migration.
- Use the shared design system tokens in `StyleConstants.swift`.
- Keep the Figma warmth: cream cards, orange accent, rounded cards, calm spacing, and friendly devotional tone.
- Avoid adding generic placeholder UI when existing content exists. Prefer wiring existing content into the new shell.

## Branch Workflow

- Use branch names prefixed with `codex/` unless the user requests another prefix.
- Every feature branch must include an `implementation.md` at the repository root.
- `implementation.md` should explain the branch purpose, scope, product decisions, files changed, validation, and follow-up work.
- Do not mix unrelated backend/admin/database migrations into a UI branch unless the implementation document explicitly says so.
- Keep user or autogenerated dirty changes intact. Never revert unrelated files without explicit approval.

## Implementation Notes

- Prefer SwiftUI-native composition with small focused views.
- New bottom-tab screens should be first-class pages instead of temporary overlays.
- Use local state for screen UI where possible and shared app state only for app-level concerns such as selected language and selected tab.
- Existing Firebase models should be reused for current content:
  - `NewsletterViewModel` for Connect announcements and weekly newsletter.
  - `AuthManager` for content access and account state.
  - `WordCardViewModel` and `PraiseViewModel` are legacy/reusable services, not first-level Resources dependencies in this phase.
- Daily Verse legacy read/like state should go through `VerseEngagementService`, remain local-first through App Group shared defaults, and sync to `users/{uid}/verseEngagement/{reference}` only when a Firebase-authenticated user is available.
- Daily Verse favorites and Bible Reader favorites should share `FavoriteService`, remain local-first for signed-out users, and sync signed-in data under `users/{uid}/favorites/{favoriteId}`. Notes require login and live under `users/{uid}/notes/{noteId}`.
- First-phase Resources should use Firebase-backed `resources` with local seed fallback. The Resources tab can host first-class tools such as the native Bible Reader and Favorites page without putting Firestore calls directly in SwiftUI views.
- Future regional access should be prepared through clear UI boundaries and naming, not hard-coded prematurely.
- Legacy pages such as `ConnectView` and `WordCardGalleryView` should stay in the codebase until a cleanup branch verifies no previews, project references, or future reuse paths need them.

## Graphify Workflow

- Before starting new coding work, agents should use the Graphify skill to understand the repository graph and relevant dependencies.
- If Graphify is not installed or not exposed in the current Codex session, record that fact in the work log and continue with ordinary code search (`rg`, file reads, Xcode build settings).
- Do not invent Graphify output. Treat Graphify as a required discovery step only when the skill/tool is actually available.

## Firebase Development Workflow

- Firebase development and tests must use the local Firebase Emulator Suite first. Do not default to reading from or writing to production Firebase while developing features.
- Use `firebase emulators:start --only firestore,auth` or `scripts/firebase-emulator-start.sh` before emulator-backed tests.
- Seed only emulator data with `scripts/firebase-seed-test-data.js`; the script must require `FIRESTORE_EMULATOR_HOST` and `FIREBASE_AUTH_EMULATOR_HOST` so it cannot accidentally seed production.
- App, service, and test code should support dependency injection for Firestore, Auth/current user id, and UserDefaults/shared defaults where practical.
- Firestore schema changes must be reflected in `firestore.rules`, `firestore.indexes.json` when needed, `README.md`, and `implementation.md`.
- Rules changes must be validated against the emulator before production deployment. Production rules/index deployment should only happen in an explicitly scoped backend/deployment branch.
- Login, approval, and branch-church work must preserve legacy `users/{uid}.role == "admin"` compatibility while adding scoped `accessRole` values (`global_admin`, `region_admin`, `branch_admin`, `member`) and normalized `orgId`, `regionId`, and `branchId` fields.
- Scoped user-management writes for region and branch admins should go through callable/server-side boundaries such as `setUserAccessAdmin`; do not open direct client Firestore writes for delegated admin actions without emulator rules tests.
- First global admin bootstrap must use `scripts/firebase-bootstrap-global-admin.js` in dry-run mode first, then `--confirm-global-admin` only after explicit production approval. This script is responsible for keeping Firestore profile fields and Firebase Auth custom claims aligned.
- Production branch initialization must use a dry-run first. `scripts/firebase-seed-branch-system.js` requires `--confirm-branch-system` before it patches production users or writes `organizations`, `regions`, `branches`, and `branchMemberships`.
- Never commit real Firebase secrets. Keep `GoogleService-Info.plist` ignored and provide example/setup documentation instead.

## Validation

- At minimum, run a Swift parse or Xcode build after Swift UI changes.
- Prefer an Xcode simulator build when navigation, sheets, or Firebase-linked views change.
- Document validation results in `implementation.md`.
- If validation cannot be run, record why and what residual risk remains.

## Admin Portal And Backend Priority

- Admin portal changes are required for the larger branch-church product, but they are lower priority than the current Figma UI merge.
- Backend/database cleanup should be handled in a separate branch with its own `implementation.md`.
- Regional role allocation should eventually support local admins assigning users to branches/groups, but current UI branches should avoid inventing final authorization rules.

## graphify

This project has an AST/code knowledge graph at graphify-out/graph.json. Full semantic reports, god nodes, and community labels require a later full Graphify extraction with an LLM API key.

When the user types `/graphify`, invoke the `skill` tool with `skill: "graphify"` before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only if it exists and only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
